6. **허들은 광고를 "절반쯤" 보는 플레이 기준으로 잡는다** (11:31 추가, 14:27 수정 — 무광고 기준이면 광고를 보는 유저에게 시간 장벽이 없어진다). 기준선 = 광고 기회마다 50% 시청: 광고 상자는 나온 것의 절반, 앱 밖 정산 2배는 세션 절반, 광고 뽑기는 하루 4종 중 2종, 던전 광고 입장은 던전마다 하루 1회(2회 중), 광고 퀘스트는 그 시청 수로 깨지는 만큼. **무광고와 광고 전부는 민감도**로 본다 (11-03 사용자 정리, 최종 12:28):
   - 허들(시간 장벽)은 **중~후반 구간** 이야기다. 초반(첫날~첫 주)은 D6·D9대로 막힘 없이 흐르게 한다.
   - 허들과 시간 장벽은 **적당히(절반쯤) 광고를 보는 유저** 기준으로 세운다. 모든 광고를 보는 플레이를 기준으로 잡지 않는다.
   - 광고 보상은 **들인 시간에 비해 좋은 보상**이다 — 광고를 보는 유저는 무광고 유저보다 허들을 쉽게(빨리) 넘는다.
   - 그래도 **모든 광고를 매일 챙겨 보는 유저에게도 약간의 허들은 남는다**(허들이 작아질 뿐 없어지지 않음).
   - 무광고도 막히지 않는다(더 느릴 뿐).
   - **첫 1시간(플레이 시간)은 성장의 재미와 동기**: 5분 이상 걸리는 허들을 두지 않는다 — 강화·스테이지가 계속 올라 성장 곡선을 제대로 느끼게 한다 (11-03 12:28 사용자, 무광고 포함).
   - **그 뒤 어느 스테이지부터는** 시간 장벽(방치·앱 밖 보상으로 넘는 허들)을 두고, **결제나 광고로 완화**할 수 있게 배치해 동기를 계속 이어 간다 (11-03 12:29 사용자).
   - **(14:28 확장) 광고 시청 지표 + 광고 BM과 연결:** "절반"을 감으로 두지 않는다. research가 방치형 RPG의 리워드 광고 지표(시청 유저 비율, 시청 유저당 하루 시청 수, 상위·하위 구간 분포, 배치별 시청률, eCPM 범위)를 찾고, theory가 유저 구간(무광고 / 가벼운 / 보통(기준선) / 많이)을 정의해 **광고 1회 가치(몇 분치 진행)·배치별 하루 횟수·구간별 허들 체감**을 BM 수치안으로 낸다. 기준선은 그 지표의 "보통" 구간. 코드는 관리자가 배치별 시청 수 기록(나중에 분석 SDK로 보낼 자리)을 넣는다.
7. **수치 증가 체감** (14:21 추가): 레퍼런스 방치형은 강화 1~2레벨마다 "0.1c", "1a"처럼 표시 수치가 크게 뛰는데, 우리 게임은 레벨당 +1~2(공격력 10+2·Lv)라 성장이 체감되지 않는다. → 능력치·적 체력·골드·비용의 **자릿수 스케일을 키우고**(레벨당 증가량이 레벨과 함께 커지는 곡선) 표시는 **알파벳 단위(1a = 1,000, 1b = 100만, 1c = 10억 …)**로 바꾼다. 표시 단위는 관리자가 코드로, 곡선(perLevel 성장 방식·스케일)은 theory 수치안에. 값은 long(9e18) 안에서 끝나는지, 넘으면 double 전환이 필요한지 함께 적는다.
8. **높은 등급이 무조건 좋다** (14:25 추가): 장비(무기·방어구·펫)는 **높은 등급의 Lv1이 낮은 등급의 최대 레벨보다 보유·장착 효과가 커야** 한다. 지금은 아니다: 등급 ownBase 2/5/15/40/100, 레벨 배수 1+0.2·(Lv−1)(Lv100 = ×20.8) → 일반 Lv100 41.6% > 영웅 Lv1 40%. 해결안(등급 간 배율 확대 = 기준 7과 함께, 등급별 최대 레벨, 등급별 레벨 보너스 등)은 theory가 고르고 근거를 적는다. 꼬마(attackMultiplier 0.8~1.2)는 지금 등급 순서대로라 그대로 둔다(같은 원칙만 확인).
   - 지금 던전: 던전 1만 내용이 있다(InGame 수확 판, `InGame/HarvestGame.cs`·`StageProgress.cs`·`DungeonTickets.cs` 하루 2회, 해금 스테이지 5/15/30/80/150은 던전 시트). 기능 구현은 관리자가 밸런스 수치와 함께 한다.

## 흐름

기본 순서는 조사 → 이론 → 검증 → (관리자가 적용) → 테스트. 그 위에 **누구든 누구에게나 요청**한다(이론이 근거 필요 → research, 측정 필요 → test, 테스트가 차이 원인 → theory, 검증이 실측 필요 → test …). 넷 다 동시에 시작하고, 앞 단계 결과가 없으면 지금 있는 것으로 먼저 하고 가정을 적는다.

## 공유 규칙

- **한 파일 = 한 작성자.** `현황/<내이름>.md`와 내 산출물만 쓴다. 남의 파일은 읽기만
- **요청 확인:** 시작할 때 · 단계마다 · 끝내기 직전에 `python 밸런스설계/요청보기.py <내이름>`. 나에게 온 요청(관리자 것 먼저)을 하던 일보다 먼저
- **요청:** 내 파일 "요청"에 `- [ ] #번호 → 대상: 무엇 · 왜 · 받고 싶은 형태 (시각) [막힘|참고]` — `[참고]`는 가정 두고 계속, `[막힘]`은 할 게 없으면 반환에 `대기: 내이름#번호`
- **답:** 받은 쪽이 자기 파일 "받은 요청 처리"에 `- [x] 보낸이#번호 → 답 · 결과 경로 (시각)` (못 하면 `거절: 이유 · 대신 누구에게`)
- **정정 요청에 동의하지 않으면** 근거를 답에 적는다(무조건 따르지 않는다)
- **알림:** `[막힘]`을 올렸을 때, 산출물 초안이 나왔을 때, 끝날 때 SendMessage(to: "main") 한 줄
- **코드·표(`Assets/`, `GameBalance.xlsx`)·사용자 문서는 관리자만 쓴다**
- 시각은 **반드시 `date +%H:%M`**으로 확인해 적는다

## 관리자

- 할당은 `현황/manager.md` "요청"에 `manager#번호 → 대상`으로 적고 띄운다(끝난 에이전트는 SendMessage로 이어서)
- 산출물 수치는 원 기록으로 직접 다시 계산해 확인 → `검증: … 확인` 또는 정정 요청
- verify 통과안만 적용, 사용자 결정 전 구조 변경은 기본 꺼진 실험 플래그로만
- 같은 요청이 3번 넘게 오가거나 사용자 몫(목표·기준·구조)이면 멈추고 사용자에게 묻는다
